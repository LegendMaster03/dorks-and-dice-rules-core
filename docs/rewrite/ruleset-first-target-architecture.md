# Rules Core rewrite — ruleset-first target architecture

Status: **architectural direction**, 2026-10-09. This describes the intended product, not an already implemented design or a final choice of game mechanics.

## Mission

**Implementation order (owner direction, 2026-10-18):** **Native foundation → basic operational rules → each rules subsystem together with its source-conversion mappings → unified converted stat-block catalog → consumers.** The old assumption that *the entire ruleset* must be designed before any engine code is replaced by **foundation approval plus subsystem-level design/acceptance before implementing each slice**. Internal DB stat blocks and external source stat blocks must share an authoritative native projection; imported source material must pass through Dorks & Dice conversion before use. Reusable automated mappings should resolve established equivalences **without recurring Rules Lawyer attention**, while ambiguous/conflicting content remains reviewable. This ordering takes priority over earlier instructions in this document to integrate Block Initiative before developing the core mechanics.

**Current implementation and availability premise (owner correction, 2026-10-18):** The old Rules Core is **hidden and has had public/tester access disabled for about a month**. **Block Initiative is the sole public/tester-accessible Tool**; its Rules Core dependency is **optional monster stat-block autofill** (the current client also exposes condition autocomplete). **Character Sheet is deliberately development-only** and is the largest mechanics consumer. No other Tool is presumed to need a fully operating Rules Core in public/tester use. Build **one new native implementation in the existing service/repository**, not parallel old/new services, a dual runtime or a deployment cutover. Scope consumer integration by actual needed rules/data rather than making a publicly deployed full-system engine a precondition of Block Initiative's optional lookup.

Rules Core is becoming the authoritative host and execution engine for the **Dorks & Dice custom tabletop role-playing game system**. It is no longer primarily a program that resolves between external tabletop rulesets. The Dorks & Dice system itself defines the primary vocabulary, mechanics, applicability, interaction policies, and defaults. Rules from 3e, 3.5e, 5e, 5.5e, and additional compatible sources are imported and reconciled **into** this hosted system and with one another.

This is a more fundamental change than moving the existing house-rule baseline into a separate source package. **The game system is not being invented from zero**: the existing cross-edition resolver has already made numerous substantive Dorks & Dice design decisions when recognizing equivalent mechanics, preserving distinct calculations, building universal competencies, and deciding how imported rules coexist. These choices are the starting design evidence for the independent system, not architectural code to copy wholesale. The custom system must ultimately constitute a playable, independently versioned ruleset whose procedures operate without silently selecting an older edition as the default. We must recover and verify previously settled decisions while identifying genuine design gaps, not reopen everything as if it had never been considered.

Compatibility remains a fundamental objective. Moving authority to Dorks & Dice must not erase mechanically important differences, discard imported options, or force false equivalence among editions.

**Governing play-experience requirement (owner, 2026-10-09):** Dorks & Dice must work for **an all-basic table, an all-advanced table, and any mixture of player complexity preferences**. A player who prefers the comparative simplicity of 5.x can play in the same encounter as one who prefers the depth of 3.x, but **neither playstyle requires players who prefer the other one to be present**. Each player chooses how deeply to interact with mechanics, including changing depth from one activity to another. All share one coherent Dorks & Dice rule/effect system. Accept source-edition compromises when necessary to maintain this composition-independent play. This is a **game design constraint on conversion, engine semantics and user-facing projections**, not authorization to implement a particular option system.

**Purpose of the design (owner clarification):** If the goal were simply to use intricate 3.5e mechanics, the owner could run D&D 3.5e directly. Dorks & Dice exists to support **the enjoyment of playing together by participants who engage with the hobby in different ways**, such as rules mastery, tactical planning, character portrayal and storytelling. Mechanical depth is **one possible way to engage**, not the experience every player must share. Preserve authentic optional complexity and cross-player clarity, rather than implementing separate game modes or enforcing equal effectiveness as a prerequisite for inclusion.

- **Shared core:** All participants use the same effective turn/action budget, targets, defenses, damage, conditions, positions and effect semantics; no mutually inconsistent source-edition modes per player.
- **Player-selected depth, without parity requirement:** A straightforward character and an involved tactical character both have usable paths through combat. Richer options may legitimately create **greater versatility, capability, and power** because a player chooses and masters more complex mechanics. **Equal effectiveness is not required.** Ordinary play must not depend on learning another character's procedures, and optional complexity should not be mechanically flattened merely to give simple play the same benefits.
- **Emphasis uses sum-to-21 cancellation (owner-approved player wording):** Keep Normal, Advantage, Disadvantage and Emphasis as distinct roll modes. Use the **owner-approved player-facing text verbatim** from the [native Emphasis specification](native-rules-design-specification.md#emphasis-within-attackerdefender-effect-attribution), rather than substituting a shortened paraphrase. If the two dice add up to 21, apply an **explicitly defined, applicable cancellation effect** if one exists; **otherwise reroll both dice together**, repeating if necessary. If the dice do **not** total 21, use the **more extreme result (closer to 1 or 20)**. **Identical dice do not cancel**; [7,7] selects 7. Examples of cancellation are [1,20], [7,14] and [10,11]. This wording preserves mathematically symmetric opposing extremes without asking players to calculate midpoint distances. A canceled pair yields no selected roll and cannot itself trigger an ordinary critical. Consumers must support repeat-roll requests and paper dice; no first-die tie substitution. This **supersedes legacy** `abs(d20-10)` scoring and first-die tie selection for the Dorks & Dice rewrite, without changing deployed legacy code at Gate 0. Roll mode overlap/precedence remains open. Escalating critical rolls stay straight and unmodified. See [native Emphasis rules](native-rules-design-specification.md#emphasis-within-attackerdefender-effect-attribution).
- **Attribute offensive and defensive effects to their actual subject:** The owner prefers **attacker-facing improvements** to resolve as attack-side roll benefits (e.g., Advantage where warranted), while **defender-facing impairments** can create native conditions, lost defenses or AC penalties. The same ownership principle applies to defensive buffs and attacker impairments. Determine an effect's **true subject and scope**, not just its 5e wording (“attacks against this target gain Advantage” may be a defender condition, while a particular attacker may gain a limited target-specific buff). Do not automatically double-count a single imported condition's Advantage and its restored 3.x AC consequences; independent, legitimately granted effects can still combine under the native stacking rules. Touch-vs-ordinary targeting remains an independent property of the incoming attack. See [attack/defense effect ownership](native-rules-design-specification.md#attacker-versus-defender-effect-ownership--representation-principle); the exact native status consequences remain open.
- **Blinded uses attacker Disadvantage, not a blindness miss-chance check (owner decision):** When a creature **attacks while Blinded**, use standard **Disadvantage** instead of the 3.x extra **50% miss roll** for a blinded attacker's lack of sight. This is a simplicity choice, **not numerical equivalence**. When the blinded creature is the **defender**, apply the established status-to-defense/AC rules; do not also grant attackers Advantage for the same underlying defensive penalty. This does not eliminate other independent concealment or source-specific miss chances. The attacker-versus-defender ownership rule and three AC types remain intact; do not reopen them simply to implement Blinded. See [native Blinded rule](native-rules-design-specification.md#blinded-keep-attack-disadvantage-instead-of-a-separate-concealment-roll).
- **Defensive status semantics with Touch/Flat-Footed interaction (review direction):** Preserve the role of 3.x defensive calculations in native statuses **case by case**. Differentiate a creature actually being **Flat-Footed**, an effect merely **denying Dexterity/dodge defenses**, and more severe helplessness/position penalties; status-based AC adjustments can be **attacker-relative** (e.g., 3.x Grappled versus outsiders). Separately, **Touch AC is primarily selected by the incoming attack/effect** (such as an initial Grapple contact or a qualifying touch spell), not automatically because the defender is Stunned/Restrained. The same attack can combine touch-targeting and a status-modified defense. Do not double-count 5e status-granted attack Advantage and restored 3.x AC penalties automatically. Review the [condition-to-defense mapping proposal](native-rules-design-specification.md#status-effects-and-defensive-ac-profiles--restoration-candidate) before approving specific native condition consequences.
- **Preserve defense roles during procedural simplification (owner direction):** Ordinary AC, Touch AC and Flat-Footed AC remain meaningful native defenses where their 3.x physical/rules purpose applies. **Grapple now has a selected 3.x native foundation:** ordinary initiation tests **Touch AC for contact**, then uses an **opposed grapple check** for control; escape may use an opposed grapple check or the separate Dexterity-based **Escape Artist** skill against the grappler's check. Athletics and Acrobatics are **not substituted for Escape Artist** in the native mechanic, and proficiency from different sources must not double-count or silently collapse these skills. This is a 3.x-native Grapple choice rather than adding a Touch AC stage onto an otherwise unchanged 5e contest/save. Native Reaction/provocation, movement, detailed Grappled/Pinned consequences and mixed-character conversion still require reconciliation with the unified combat rules. Feature-specific automatic grapples may have authorized exceptions. See the [selected native grapple procedure](native-rules-design-specification.md#native-grapple-baseline--3x-procedure-with-escape-artist).
- **Effect normalization, not false procedural equivalence:** Shove, Topple, Trip, Push, spell and class-feature effects can share a displacement or condition executor while preserving each source's authorized attack trigger, save/check, action cost, limitation and acquisition requirements.
- **Preserve worthwhile complex mechanics:** Keep rule procedures detailed where simplification would remove their meaningful tactical or character-building capabilities. The owner accepts that advanced players may be stronger and more capable; the goal is **opt-in complexity within a shared playable ruleset**, not balance equivalence across complexity levels. Continue enforcing actual prerequisites, source-granted extra actions, resource expenditures, and limits so automated conversion does not accidentally create *unearned* advantages.
- **5e-style arithmetic simplicity is optional; each table chooses who calculates:** Prefer familiar, simpler 5e methods where appropriate, but **do not impose a hard player arithmetic ceiling or require the DM to perform all remaining multiplication/division**. The DM may calculate a creature's damage resistance/vulnerability privately or disclose the relevant damage-type properties and allow players to apply the arithmetic; other retained 3.x fractions, multipliers or percentages can likewise be worked by either side as suits the table. Digital tools should calculate correctly and support permission-appropriate DM/player workflows **without forcing disclosure of hidden monster traits or role-based math ownership**. Rules, rounding and stacking remain deterministic; the flexibility concerns calculation workload and information disclosure, not permission to change defined outcomes. See [arithmetic simplicity and table discretion](native-rules-design-specification.md#arithmetic-simplicity-and-table-discretion--5e-style-preference-not-a-requirement).
- **Arithmetic simplification as a source-reconciliation heuristic:** Prefer existing, readable 5e-style expressions for 3.x percent rolls, multiplication and division **when they preserve the underlying mechanic's purpose closely enough**, applying existing Dorks & Dice rulings first. A **Blinded attack uses Disadvantage** instead of its separate 3.x 50% miss check; this illustrates simplification, not numerical equivalence. Roll-side modifiers (Advantage/Disadvantage/Emphasis) affect d20 odds, **not damage amounts**. Retain meaningful damage/resource/progression calculations including 5e's own half/double damage, and keep 3.x distinct source features such as fractional weapon ability-modifier scaling under review rather than erasing them automatically. Apply targeted conversions case by case with provenance and stacking checks. See [native arithmetic simplification direction](native-rules-design-specification.md#arithmetic-simplification--prefer-existing-5e-expressions-when-meaningful).
- **Reuse-first source comparison, not three source-edition engines:** For remaining combat rules, first assess whether the 5e procedure is an accessible version of a 3.x concept and can serve as the shared Dorks & Dice baseline. Preserve legitimately granted richer 3.x functionality as appropriate native options or extensions, then resolve **actual differences on a case-by-case basis** using the adopted house rules and shared-complexity design. Do not force a 5e procedure where its rolls, prerequisites, costs, or consequences materially differ (for example grappling), or falsely equate BAB full attacks and Extra Attack. Reuse verified rules and retain provenance, but require explicit native decisions for incompatible cases. This approach reduces novel game-design work; it does **not** authorize duplicated 3.x/5e combat runtimes, blanket source precedence, or unearned feat grants.
- **Combat-area design matrix and three depth patterns:** Use the [native rules specification's shared-foundation/optional-depth matrix and three patterns](native-rules-design-specification.md#combat-design-matrix--common-rules-selectable-depth) to evaluate combat options: **simple action with advanced alternatives**, **additional features on an ordinary action**, or **optional cooperative procedures**. These are design patterns, not separate combat modes or authorizations to feat-lock ordinary source features. The same Reaction allowance applies to ordinary and specialized reactive choices unless a distinct feature explicitly provides otherwise. Each row's unresolved trigger, acquisition, timing or calculation remains subject to owner review.
- **One shared mechanic, selectable complexity (owner-endorsed design direction):** Specify a complete ordinary action with shared resolution, condition and resource semantics. Characters with valid feat/class/other grants can select substantially more capable or intricate expressions of that same action, **without changing the ruleset or action budget**. Advanced features may grant extra *choices* or *permitted triggers* for the existing Reaction, **not extra Reactions** by default. Evaluate whether the added complexity represents meaningful character capability or merely a more detailed way to present the same computation; only the former may warrant feat acquisition. Avoid permanent player complexity labels, forced power parity, or a generic requirement to unify unrelated systems such as combos and Weapon Mastery. Existing GM discretion to award advanced feats for free is a character/campaign grant, not an automatic baseline.
- **Feature-granted advanced alternatives without extra action resources:** Where an elaborate mechanic represents a substantial **additional capability**, consider expressing it as a feat/class-feature grant that expands **eligible choices or triggers for an existing Action or Reaction**. The owner specifically distinguishes more things a character may do with the **same Reaction** from receiving more Reactions. Do not expand the reaction count by default. An opportunity attack might be replaced by an eligible reactive maneuver; additional allowed provocation conditions may create choices without extra reaction slots. This is a candidate design pattern, not mandatory feat-locking of all complex source rules. Preserve ordinary functionality, source-granted feature access, per-character budgets, and the distinction between mechanically significant combat feats and freely granted flavor feats.
- **Discretionary awards are not default feat entitlements:** The ordinary cost and qualifications of mechanically substantial combat feats remain the native ruleset default. A GM can make an explicit exceptional free award to one or more characters, including at an advanced table, but **veteran status and party composition do not automatically grant free combat feats**. Model awards as authorized campaign/character grants with GM-decision provenance, not an altered global feat progression. A grant expands feat access, not the available Reaction count. This is separate from the established generally free **flavor feats** policy.
- **Consequence-focused consumer API:** Character Sheet and game Tools should be able to expose a simple actionable view and optional in-depth explanations using the **same effective rule resolution**, not separate simplified numerical physics. A player only needs an understandable outcome from another player's advanced ability; GM adjudication and authorized campaign options remain available.
- **Optional specialist participation, not a mandatory party composition:** Loot Tavern's Harvesting & Crafting Lite permits interested characters to undertake specialized Assessment/Carving roles and qualified helpers to contribute under its published limits. A mixed party can distribute the complexity; an advanced party can have several interested participants fulfilling the **actual permitted** specialized and helper roles; a basic party can decline to engage with this optional subsystem and still play a complete adventure. Recover the implementation's helper eligibility, proficiency contributions and creature-size participant caps as evidence, but do **not** generalize its specific roles or calculations to combat or force any table to designate an advanced leader.
- **Cooperation that scales with the group:** Standard initiative and optional Block Initiative both permit cooperative combat at **all-basic, all-advanced and mixed tables**. Block Initiative offers a particular coordination structure but is never compulsory. Loot Tavern harvesting provides a separate helper-participation pattern; it does not define combat contributions. Preserve individual action ownership, character agency and the actual constraints of optional specialized activities.
- **Parallel optional combat additions:** Loot Tavern's *Ryoko's Guide to the Yokai Realms* supplies examples of **cooperative combo attacks**; 2024 and Ryoko Weapon Mastery supply **additional character/weapon attack features**. Combos do **not replace ordinary combat** and mastery does not define the root combat procedure. Ryoko's **source procedure already uses standard initiative**, with an initiating attack on the instigator's turn and eligible collaborators using reactions in initiative order. **No Block Initiative-specific combo rule adaptation is necessary**: the preserved initiative order determines collaborator reaction sequencing, independent of the freely chosen allied turn order within a block. Verify definitive source-specific costs, critical stacking and eligibility before adopting. Do not treat preliminary playtests as final or require an imported subsystem in order to perform ordinary attacks.
- **Validation across initiative and table compositions:** Test all-basic, all-advanced and mixed groups using **standard initiative and Block Initiative separately**. Ordinary attacks, maneuvers and Weapon Mastery must not require combo participation, and combos must not require Block Initiative. Check reactions, start/end-of-turn durations, action costs, criticals and coordination independently in each mode. Separately test voluntary use or nonuse of harvesting. Do not require exact effectiveness parity or a mandatory digital tool.

**Design-to-code boundary (owner revised direction):** Approve the **common mechanical vocabulary, minimum native rule behaviors and acceptance fixtures** before writing the kernel. A **complete playable Dorks & Dice game remains the eventual goal**, but its full specification is **not a prerequisite for beginning foundation implementation**. For each later subsystem, review its native rule, interactions and source conversion rules **before building that slice**. Existing recovered rules and generalized Level Bands are inputs rather than blank-slate problems. See the [phased implementation plan](foundation-and-cutover-gates.md#incremental-implementation-sequence--native-foundation-one-complete-system-at-a-time). This update does not authorize merge, deployment, access restoration or destructive schema changes.

**Compatibility premise:** as Pathfinder First Edition was compatible with D&D 3.5e through manual conversion, Dorks & Dice aims for **automated** rule/content conversion from 3e, 3.5e, 5e (2014), and 5.5e (2024) into its own governing rules. PF1e is a potential additional source. Automated conversion includes faithful automatic mappings where provable and explicit review states for ambiguous or incompatible cases; it does not assert that different numeric systems or source rules are identical, or promise lossless migration of every existing character and campaign.


## Clean-slate implementation and licensing

**Starting from scratch means a clean native rules engine and implementation architecture, not discarding existing Dorks & Dice mechanics decisions or treating previous work as absent.** **Greenfield implementation is the default**: author new domain entities, rule-composition semantics, engine code, and persistence without inheriting the old resolver's class structure or database as constraints. Existing source pipelines, fixtures, API contracts, and cross-edition conclusions are reference material and migration targets, not building blocks that must be copied. Retain the historical service unchanged while the replacement is constructed and verified. Inventory the existing solver's adjudications, stable universal concepts, cross-edition relationships, mechanics contracts, and accepted house rules. Distinguish established design policy from incidental translation behavior, temporary fallbacks, and implementation constraints. Reimplement established policy deliberately under the new Dorks & Dice ontology.

Under United States copyright law, 17 U.S.C. § 102(b), abstract game procedures, systems, processes, and methods of operation are not protected by copyright. Original explanatory text, artwork, and other expressive content can be protected. The D&D SRD 5.1 and SRD 5.2.1 are **not public domain**; Wizards released them under **Creative Commons Attribution 4.0 International**, allowing use, adaptation, distribution, and commercial reuse with required attribution. The **3e and 3.5e SRD** publications and independently licensed third-party source bodies have different permissions (not a blanket CC BY 4.0 grant) and require separate source-specific handling; the availability of a game mechanic does not itself authorize reproducing someone else's protected explanatory text. The distinction matters when we choose between independently authoring descriptions/implementations and incorporating actual SRD material.

### Pathfinder First Edition as the 3.x precedent

**Pathfinder First Edition is our concrete precedent for reusing and adapting 3.x mechanics within an independent TTRPG.** Paizo's March 18, 2008 announcement said that Pathfinder's rules were based on D&D 3.5 Open Game License rules, with backward compatibility as a primary goal. This demonstrates an established historical route: preserve the familiar mechanical foundation, introduce a distinct game's rules and changes, and publish designated open content under its applicable license.

Dorks & Dice need not adopt Pathfinder's actual choices or copy its implementation. For 3e/3.5e-derived mechanics, distinguish these routes per material:

- **Independently implemented methods of play.** U.S. copyright law does not protect abstract procedures, systems, or methods of operation under 17 U.S.C. § 102(b). Write the Dorks & Dice engine and explanations independently, without copying protected prose, illustrations, setting expression, or trademark presentation. The precise copyright/expression line may still require examination for an individual rule.
- **Text or other content explicitly released as Open Game Content.** Material taken under OGL 1.0a must follow that license's terms, including required license/copyright notices and exclusion of designated Product Identity. Pathfinder 1e's use of OGL 1.0a is the model for this route.
- **Materials published under other licenses.** SRD 5.1/5.2.1 CC BY 4.0 content, ORC-licensed Pathfinder material, and restricted third-party works must be tracked separately. The release of mechanics under one license does not relicense OGL-only material under CC BY or ORC, or license trademarks and worldbuilding.

Paizo's newer ORC-era Pathfinder publications are not interchangeable with Pathfinder First Edition's OGL foundation. Use Pathfinder 1e as the precedent for **3.x mechanics and OGL practice**, not as a blanket license from Paizo or Wizards. If publishing a substantial compilation that actually incorporates licensed game-rule expression, review the content and notices before release, particularly where multiple source licenses meet.

## Optional combat layers and initiative alternatives

**Source-timing correction (2026-10-09):** Ryoko combo attacks **assume normal individual initiative**, rather than needing a new standard-initiative design. Available rules text has an instigator declare an attack on their own turn, collaborators spend reactions in initiative order, and the instigator then rolls. **The owner confirms no separate Block Initiative combo adaptation is needed**. The source combo procedure applies as written in both initiative modes; independently open action-economy and critical interactions are not evidence of an initiative incompatibility. This is evidenced by accessible copies, including beta playtest text; verify final published details before hard-coding numerical effects or edge-case restrictions.

**Block Initiative compatibility correction (2026-10-09):** **No rules adaptation is necessary for Ryoko's combo attack sequence.** Block Initiative preserves combatants' initiative ordering while permitting allies to choose a different tactical turn order inside a block. The instigator still declares on their own turn, contributors spend reactions in initiative order, and the attack resolves afterward. Preserve the original combo procedure under either initiative selection. The existing [initiative engine](https://github.com/LegendMaster03/dorks-and-dice-block-initiative/blob/main/src/BlockInitiative.Core/Initiative/InitiativeEngine.cs) and [TurnBlock implementation](https://github.com/LegendMaster03/dorks-and-dice-block-initiative/blob/main/src/BlockInitiative.Core/Initiative/Blocks/TurnBlock.cs) independently retain those facts. There is no need to invent a combo-specific variant, reaction budget or resource refresh for Block Initiative.

**Owner clarification (2026-10-09):** Dorks & Dice needs a **standalone ordinary combat system** that can use either **standard initiative or optional Block Initiative**. It must not rely on Block Initiative to function. Weapon Mastery is **an additional way for eligible characters to interact with ordinary attacks**, and cooperative combo attacks are **a parallel, optional system**, not a replacement for normal combat. Combat maneuvers retain their own deliberately specified procedures. The prior *Combat Techniques* unification proposal was a deliberately provocative test and was not approved; it must not drive architecture.

These are **distinct mechanics connected by defined interfaces**, not interchangeable player-facing modes:

| Mechanic | Responsibility | Must not assume |
| --- | --- | --- |
| Ordinary combat | Actions, movement, ordinary attacks, damage, defenses, conditions, and opportunities to undertake maneuvers | Weapon Mastery, cooperative combos, or Block Initiative are enabled |
| Initiative selection | Select between **standard individual turns** and optional **Block Initiative** turn/block order | Selecting a mode changes what ordinary attacks or character features exist |
| Weapon Mastery | Apply appropriately granted weapon-specific hit, miss, damage, effect and attack-sequencing modifications | Mastery is available to all weapons/characters or becomes the attack engine |
| Cooperative combos | Resolve opt-in multi-character coordinated attacks. Ryoko's reference starts with an attack on the instigator's turn; eligible allies use reactions in initiative order before the roll. | A combo replaces ordinary attacks, adds free actions by default, or requires Block Initiative |
| Maneuvers | Resolve defined intents such as grapple, trip and disarm with their own requirements and consequences | The same formula or participant rules as weapon mastery or combos |

**Acceptable shared primitives** include attacks, action/reaction costs, targeting, saves/checks, position changes, damage and conditions. For example, several features may cause Prone; sharing Prone's meaning is correct, while replacing every source trigger with one maneuver formula is not. Actual workflow and cost integration need explicit gameplay decisions, including under **both initiative options**. No single new `Combat Techniques` subsystem is mandated or approved.

**Critical design-review questions:** **Preserve Ryoko's already established reaction/turn procedure unchanged for both standard and Block Initiative.** Its initiative-based contributor order is available even when members of a block choose a different order for their own turns. Do not propose changes absent a concrete conflict. Is ordinary combat still self-sufficient if combos are never chosen? Does Weapon Mastery remain character/feature-gated? Can advanced features trigger multiple unintended effects, or force more complexity on players who did not opt in? These are genuine tradeoffs to evaluate rather than presumed benefits of unification.

The [native rules specification](native-rules-design-specification.md#combat-maneuvers-weapon-mastery-and-combo-attacks--distinct-roles) records the distinct gameplay roles and remaining open mechanics.

See the [proposed feature-gated advanced mechanic pattern](native-rules-design-specification.md#feat-granted-advanced-expressions-of-basic-combat-mechanics--proposed-design-pattern) for the owner's clarification that expanded Reaction choices do **not** imply additional Reactions.

## Generalized Level Bands and advancement-track semantics

The old `docs/epic-content-modeling.md` preserves a record of the legacy implementation's epic normalization; **the new Dorks & Dice ruleset does not use epic as an engine-level special case**. Instead, 20-level **Level Bands** apply to relevant level-based tracks (1–20, 21–40, etc.). Character total level, each class progression, and each separately leveled prestige progression may be in different bands concurrently; a subclass inherits the effective parent-class track. A feature may determine acquisition, effect scaling, and prerequisites from different named tracks.

A rule's band/threshold behavior may introduce the mechanic, preserve it without new improvements, continue its progression, evolve its behavior, or terminate its effect; absence of a rule must not be confused with a default transition. Labels such as **Epic Feat**, **Epic Boon**, and **Epic Spell** remain source/catalog descriptors, not a separate level-21 algorithm. Full details and unresolved defaults belong in the [native rules specification](native-rules-design-specification.md), not in persistence or translation assumptions.

## Aspirational play-at-the-table compatibility for existing 5e characters

**Stretch goal, not an implementation commitment:** Beyond conversion of rules/content and beyond ensuring Dorks & Dice characters can choose different levels of complexity, the owner would like a guest who arrives at a one-shot with a preexisting 5e character sheet to be able to play reasonably well **without rebuilding the character**. This may involve DM adjudication and imperfect translations. It must **not become a hidden release gate, a demand for automatic lossless character-state migration, or parallel player-specific 5e combat rules**.

The potential future design is a **thin compatibility bridge**: use the existing sheet as a practical input/reference, respect Dorks & Dice shared encounter rules and the selected standard or Block Initiative option, accept familiar printed stats where their use is meaningful, and provide explicit one-shot GM mapping for absent or incompatible statistics, costs and effects. In particular, **Touch and Flat-Footed AC cannot be inferred to equal ordinary 5e AC**, source features may involve incompatible action costs, and 2014 and 2024 5e characters may not have identical options. DM-visible uncertainties are preferable to fabricated equivalence.

Keep the full Dorks & Dice native game self-contained, and keep rule/content conversion, **preexisting character migration**, and a **paper-sheet one-shot bridge** as three different deliverables. The stretch scenario should remain possible even **without** implementing a persistent import feature. Preserve enough native semantic identities and source-specific procedure fidelity to support the bridge later, but do **not** expand the rewrite's mandatory scope or replace the shared Dorks & Dice mechanics model with edition-specific play modes.

See the [native rules specification's stretch-goal examples](native-rules-design-specification.md#aspirational-stretch-goal--drop-in-5e-character-sheets-for-one-shots).

## Automated conversion boundary

A versioned adapter should identify a source's **mechanical intent**, map it into native Dorks & Dice concept/procedure/track identities, and retain its original semantics as an implementation variant when the native procedure is not equivalent. Conversion may produce: accepted equivalent, explicitly adapted, additive extension, mutually exclusive alternative, incompatible/conflicted, or unresolved/needs review. The precise accepted status vocabulary is a subsequent schema decision, not a rule to hard-code during game design.

**Rules-content conversion** is distinct from a future **character/creature/encounter/campaign migration** tool, because converting a class feature definition does not itself decide how an existing character's rank points, levels, used spell slots or encounter conditions should map. Avoid hiding incompatible rule-system assumptions under a “successfully converted” status. Preserve source provenance, grants, history, and permissions.

### Conversion built alongside each native subsystem

For each subsystem, implement the native procedure **and** versioned mappings from eligible source implementations **in the same development slice**. A source adapter captures original text/data, source version and declared mechanics; the interpreter maps understood contributions to Dorks & Dice identities, executes approved adjustments and preserves source-specific differences. A tested mapping can be reused across many related creatures, items and publications; adding a new imported book should not require a Rules Lawyer to adjudicate every equivalent spell, skill, defense or action.

The **Rules Lawyer reviews actual unknowns**, such as non-equivalent costs, unresolved combinations, conflicting precedence or unrecognized source behaviors. An accepted, scoped ruling may become a reusable mapping rule, including version/provenance and campaign/source limits, but must not become an unrestricted global equivalence. Until adjudicated, retain source-native data and expose a clear unsupported/unresolved state rather than executing guessed mechanics. Decisions should survive re-imports and mapping-version upgrades; idempotent translation must not create fake source revisions or duplicate canonical/physical-source records.

### Native stat-block projection from internal and external sources

An internally **authored Dorks & Dice stat block** already uses native mechanic identities; an **imported stat block stored in the internal database** and an **external source stat block** both enter through the corresponding source preservation/interpreter/conversion path. **All three yield the same typed, authorized native stat-block projection** when the necessary mechanics are supported. Cached source records or a live external lookup must not bypass conversion because the data happen to be physically local or fetched on demand. Preserve unconverted source data and signal partial/unresolved traits where necessary.

Stat blocks compose many system slices: abilities/competencies, defenses, HP, damage types, conditions, attacks and actions, creature features and spells. Conversion of a simple monster can succeed before the most elaborate monsters are covered; **do not mark a partly understood creature as fully converted**. Preserve separate ordinary, Touch and Flat-Footed AC where applicable, with accurate source/derived values and optional native calculations. Honor effective ruleset version, source-content grants and import provenance. A consumer sees only permitted details, not raw unlicensed or unapproved alternate content.

## Primary architectural distinction

**Old mental model**

```text
multiple external rulesets
  -> normalize / recognize overlapping records
  -> choose, patch, or combine a source implementation
  -> expose the effective external rule
```

**Target mental model**

```text
versioned Dorks & Dice core ruleset
  -> defines mechanic concepts, behavior, evaluation, defaults,
     interaction, extension points, and conflict policy
                        |
source artifacts        |
  -> native preservation|
  -> interpretation     |
  -> semantic mapping ---+-> resolve imported rules into the core model
  -> source reconciliation----> reconcile overlapping imported rules
                                 and imported-to-core relationships
                                      |
                               accepted/adjudicated rule contributions
                                      |
                             versioned effective ruleset composition
                                      |
                      typed evaluation and Tool-specific projections
```

The Dorks & Dice ruleset is a normative input to both composition and execution. The import pipeline provides source evidence and mechanically meaningful contributions; it is not allowed to choose runtime semantics independently of the core ruleset.

## Responsibilities and boundaries

### 1. First-class hosted Dorks & Dice ruleset

- Define first-class, stable **system mechanic identities** independently of Source Layer and imported publication identities.
- Own default game procedures, applicability criteria, interaction semantics, and extension points. Authoritative mechanics must be executable/testable, not merely text rendered by Rules Wiki.
- Model the ruleset as versioned, publishable data and executable behavior with deterministic resolution snapshots.
- Allow Rules Layer adjudication to extend, replace, or deliberately override core behavior. The exact permissions, workflow, and precedence are design questions; automatic imported-source precedence is not.
- Distinguish the system's own mechanics from contributions and evidence derived from externally authored systems.
- Provide a credible path to an independent playable baseline; avoid declaring compatibility completed before the system itself is mechanically defined.

### 2. Source-native preservation and canonical recognition

The existing source-evidence guarantees remain important: immutable source artifacts/revisions, per-package grants, publication/entity recognition, lineage and origin provenance, no implicit disclosure of restricted bodies, and no fake native revision on translation upgrades.

Canonical source identity answers *what source item is this?* It does not answer *what is its Dorks & Dice meaning?* A core system mechanic has its own identity independent of both canonical source history and the Rules Lawyer's record of a particular imported implementation.

### 3. Semantic adaptation and compatibility

- Interpret native input (5e.tools, PCGen, SRDs, PDFs, later source formats) into **meaningful mechanical contributions** rather than treating any single imported schema as the engine's native ontology.
- Map contributions to existing core concepts when supported by evidence; support explicit extension concepts when a source introduces mechanics the core does not already represent.
- Record mapping relation and certainty: direct/equivalent concept, compatible facet, extension, revision/reprint, mechanically distinct variant, conflict, or unresolved. Avoid conflating a shared name with a shared implementation.
- Reconcile imported rules with core definitions **and with other imports** using shared semantic identity and interaction rules. Do not resolve a disagreement by import order, newest-edition wins, or an unexplained numeric conversion.
- Retain native calculations/profile semantics when mechanically significant until the core ruleset establishes an explicit, reviewed compatibility treatment.
- Failed, partial, ambiguous, or unsupported translation must remain visible as such, not silently approximate.

### 4. Composition, precedence, and execution

Proposed **conceptual layers** (not yet a committed runtime storage design):

1. Published Dorks & Dice system version — normative defaults and behavior.
2. Eligible, accessible imported mechanical contributions — mapped to core concepts or extensions.
3. Reviewed/global adjudication — accepted, excluded, modified, or consolidated contributions and explicit conflict resolutions.
4. Campaign rules and selected context — overrides and conditions within their authority.
5. Character/scene/action state — input facts, choices, capabilities, and transient results.

Composition must distinguish additive options from mutually exclusive implementations, prerequisites, replacements, modifiers, conditions, triggers, and explicit conflicts. Not all imported rules are automatically active. Exactly how an imported contribution becomes effective, and how core rules govern it, must be specified and tested.

The evaluator should consume a deterministic compiled/effective rules context, with stable references to its system version, rule contributions, selected decisions, and provenance. Game Tools provide state and present the resulting effects; they do not independently reimplement game logic or choose an edition to make a calculation.

### Global Rules Lawyer edits as a development-to-native feedback path

**Owner clarification (2026-10-18):** The global Rules Layer remains editable by authorized **Rules Lawyers**. Published global edits can apply while the relevant subsystem is in development/test; they are also **exportable from the database** as proposed improvements to the **native Dorks & Dice mechanic**. Rather than accumulate equivalent permanent global patches, the intended development loop is **global edit → export/review → modify the native rule definition or evaluator → test and version the native baseline → reconcile the redundant global edit**.

This is **not** automatic DB-to-source-code mutation. An export records the rule/concept identity, changed applicability/procedure/effect, source or exception scope, relevant authoring/baseline versions and provenance in a reproducible diff or structured artifact. A developer/owner reviews it and incorporates suitable changes into authored native rule data or implementation code with regression tests. Some decisions are source-specific conversion exceptions or provisional rulings and should **not** become universal baseline mechanics.

On publication of the updated native version, **do not apply the same global adjustment twice**. Track which global revision was incorporated or superseded for which native baseline; retain history and respect version-pinned campaigns where applicable. Re-exporting an already incorporated global decision should not generate another supposed change. Avoid including restricted source bodies in an unlicensed export.

**Distinguish responsibilities:** **DM campaign overrides** modify only the authorized campaign's effective rules, **user-uploaded homebrew** remains optional and selectable within eligible permissions, and **global Rules Lawyer edits** affect the shared global layer and may be promoted into native mechanics. A user homebrew choice or DM edit does not automatically become an exportable global Rules Lawyer change or require global approval.

### 5. Examples that must remain distinguishable

- **Alchemy**: a universal learned competency can reconcile 3.x ranked skills and later tool proficiency while preserving their different calculations. The core ruleset determines their interaction in a mixed character.
- **Target defenses**: Touch AC, Flat-Footed AC, standard Armor Class, advantage/disadvantage, and denied Dexterity are not interchangeable. A core procedure may use or reconcile them only through explicit applicability/compatibility rules.
- **Classes and advancement**: different advancement progressions, feat cadence, prestige prerequisites, spellcasting progression, and historically epic-labeled content must not be flattened into a 5e-only class schema; Level Bands and their per-track transitions govern native advancement. The core defines what mixed progression means.
- **Third-party rules**: new damage types, subsystems, proficiencies, or procedures need an explicit way to extend the core model, not an assumption that only known SRD categories can exist.

## Security and integration

**Consumer scope and order:** Complete the foundational native mechanics and **per-system conversion pipeline before enabling Block Initiative's optional stat-block lookup**. Block Initiative's public/tester-facing initiative operation remains independent of Rules Core; its optional monster search/detail/stat-block projection and condition autocomplete are the **first exposed consumer contract to verify after their prerequisites exist**, not the first engine feature to implement. The current Block Initiative integration uses the hosted gateway `/tool-host/registrations/rules-core/api/upstream` with resolved catalog search `/api/rules?entityType=monster|condition&q=...&limit=...` and monster detail `/api/rules/{conceptKey}`. The consumer presents HP, initiative modifiers, ordinary/Touch/Flat-Footed AC, CR and other combat statistics from the source detail; review exact permitted response shape and **manual-entry fallback** before re-enabling anything. This contract can be exercised without a general-purpose native turn, attack or damage adjudicator.

**Development-only consumers:** Character Sheet remains dev-restricted and owns mutable character state and presentation. It may integrate **one completed native mechanics slice at a time** after that slice's conversion/projection is working, instead of waiting for all optional mechanics. Rules Wiki remains the authoring/reference surface through a **private Tool-to-Tool boundary**, not a second engine. Neither Tool imposes public/tester-readiness requirements on foundational implementation.

**Privacy:** Source/grant restrictions apply even to the narrow Block Initiative lookup. No unrestricted monster details or restricted source body may be exposed merely because Block Initiative itself is public/tester-accessible. Keep public/readable Dorks & Dice mechanics distinct from permission-restricted imported sources. Public Tool operation is not authorization to re-enable all Rules Core routes or roles.

**Deployment topology:** One in-place rewritten Rules Core service, tested in its own branch and controlled environment. No parallel live old/new systems, no routing switchover, no generic legacy runtime adapter and no mandatory old-to-new cutover rehearsal. Data changes still need appropriate backups/tests, and all merges, deployments, registration/access changes or destructive changes require separate approval.

## Foundation design deliverables and per-system acceptance

**Before native foundation code**, recover the established decisions and obtain owner review of the **minimum coherent foundation**:

1. **Core native vocabulary and minimal ordinary procedures:** actor/creature identity, ability/check/save and roll selection (including accepted Emphasis wording), conditions/effects, attacks/defenses as typed concepts, basic actions/results, grants and source-independent mechanic identifiers.
2. **Versioned identity and conversion boundary:** the Dorks & Dice effective ruleset distinct from source-native data; package/physical source/edition/provenance; authorization; availability, adoption and activation; explicit unsupported/conflicted states.
3. **Executable foundation examples and tests:** at least basic native rolls, a deterministic effect result, an authorized source relationship, a restricted/denied case and a clean unresolved source case.
4. **Persistence and runtime boundaries:** evolution/versioning strategy, exact responsibilities for Character Sheet or other tool state, safe import/reprocessing, deterministic evaluation and workload controls.

**Before each subsystem code**, document and approve that subsystem's native rules, source-to-native conversion/exception policy and representative **pure native, single-source and mixed-source test cases**. Finish the independent full-system rulebook **incrementally as a result of these slices**, not as a global prerequisite for writing the foundational kernel. Mechanically meaningful 3.x rules are not flattened merely to reduce imported source variants; approved 5e-style simplifications may apply where appropriate.

**Rules Lawyer workload policy:** Routine, tested, approved translations are automatic and reusable; substantive conflict or semantic uncertainty receives informed adjudication, with the accepted resolution captured as reusable scoped rules. Manual review is not a required step for every stat block, source entity or rule. An uncertain mapping must not be silently made effective.

**Global iteration, not permanent database-only patching:** Rules Lawyers can publish global refinements during early testing; export those edits, review them and amend the underlying native mechanic where the change genuinely belongs. Record native baseline version, incorporated global decision IDs and conversion exceptions so updates are reproducible and do not double-apply. See [the global promotion cycle](foundation-and-cutover-gates.md#global-rules-lawyer-changes--export-and-promote-improvements-into-native-mechanics).

## Gate requirements

The [foundation and in-place integration checkpoints](foundation-and-cutover-gates.md) define the **foundation-first, subsystem-by-subsystem implementation order**. This owner direction supersedes the older requirement for a complete game-design freeze before engine code and the later suggestion to implement Block Initiative's lookup as the first engine slice. **Block Initiative is only reconnected after its effective, permission-filtered converted stat-block/condition queries exist**; Character Sheet and Rules Wiki remain developer-only until separately authorized. No parallel service/cutover is needed; merges, deployment, access changes and destructive persistence changes continue to require explicit authorization. Do not merely rebuild the old resolver with a Dorks & Dice house-rule overlay.

## Open questions to settle through design

- Which mechanics and procedures are the Dorks & Dice system's own defaults, and which are deliberately optional or still undecided?
- Does compatibility require exact standalone behavior for each historical edition, mixed use within one character/campaign, or both? Test the intended cases rather than assuming either.
- What is the distinction between an imported *available option*, an *adopted rule*, and an *active runtime implementation*?
- Which mechanical interactions are automatic under the custom ruleset, and which require Rules Lawyer or campaign adjudication?
- What are the versioning and migration semantics when a new Dorks & Dice ruleset version changes default behavior while existing campaigns reference older published snapshots?
- How will Rules Wiki express and author new core mechanics and external extensions without exposing unsafe or ambiguous program execution?
