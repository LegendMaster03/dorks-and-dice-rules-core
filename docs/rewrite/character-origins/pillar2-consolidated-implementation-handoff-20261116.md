## Architectural and authorization decisions to preserve

- Shared construction is **Deconstruct → Combine → Reconcile → Manifest → Reconstruct**. Biological Origination is one method-specific procedure; construct, plant, spawning, magical, and supernatural methods are separate. Both conventional Species/Ancestry and mixed backgrounds remain supported.
- Player direction, selected offers, complete physical foundation, verified native contributor eligibility, source-native choices, dependencies, and full trait progression are authoritative. There is no approved dominant Species, two-parent ceiling, random inheritance rule, or universal numerical budget.
- A previously manifested mixed contributor can transmit **only the verified current underlying configuration**, with immediate-parent identity, authoritative profile revision, and characteristic provenance. `INativeOriginManifestedContributorAuthority` and `NativeOriginManifestedContributorVerifier` implement validation but the **production authenticated profile lookup is not connected**. The in-process self-override remains test-only.
- Biological opt-in is an explicit finite first-party list, not automatic eligibility for the entire native catalog. Additional trait permissions and exact allocation prices require independent review/approval. Read-only projections do not grant traits.

### Production manifested mixed-parent lookup feasibility audit (2026-11-16)

**Existing Character Sheet components are not equivalent to production mixed-contributor authorization:**

- `CharacterOriginParentSnapshotService` validates request-local **Site owner access to both child and parent characters** before reading a committed parent Origin. It returns a narrow identity summary, not authorized underlying grants. A character's campaign association alone does not authorize access to another character.
- `CharacterOriginParentNativeReviewService` does have a server-private, current-native re-evaluation witness, but only for an **initial direct first-party Origin at stored revision 1**, with a matching single `first-party` receipt and unchanged archived draft. It rejects later reconstruction, DM mixed-Origin history, distinct Current/Underlying state and changed source records. It independently checks before/after persistence to refuse concurrent replacement. Do not weaken this gate to accept a previously mixed parent.
- `CharacterOriginParentSourceAlignmentService` matches input contributor IDs against independently owner-verified **direct** parent Species/Ancestry. Its maximum of 16 request bindings is a request-size ceiling, not a biological number-of-parents rule. It returns request-private reviewed initial profiles but explicitly does **not** authorize inherited grants or testify to an actual biological relationship.
- `CharacterOriginMixedActivationService` and `CharacterOriginMixedReviewService` currently recognize a narrow initial Human+Elf proposal (exactly two named native contributor slots, no ManifestedProfile source), under a Site-attested exact DM/campaign/target-character authority. This is not an authorized mixed-parent production construction route. `VerifiedCommittedMixedOriginReader` validates a narrow committed DM-approved `custom.human-elf` profile/receipt for **supported intrinsic and vision scalars** only; it does not independently authenticate the entire native underlying profile or offer a generalized manifested contributor authority.
- `ISiteOriginDmAccessGateway` proves DM access for an exact campaign and character; `ISiteCharacterAccessGateway` proves owner access for the request character. Neither alone defines a cross-owner parent-sharing, parent-consent, lineage or child-use entitlement. The existing in-process test self-override may not substitute for this absent server-side policy.
- Rules Core's `INativeOriginManifestedContributorAuthority.ResolveCurrent` expects a synchronously resolved, exact profile + revision for a trusted scope. Production Character Sheet/Site authorization is asynchronous and the data can change while native construction runs. A future adapter must assemble request-local, server-only verified witnesses, resolve them without client-selected authority data, recheck source characters' immutable event receipts and revisions at the child commit boundary, and handle independent source edits conservatively.

**Result:** It is **not safe** to wire the existing parent snapshot or `VerifiedCommittedMixedOriginReader` directly into first-party mixed-descendant transmission. The next implementation requires an explicitly defined Site-authoritative parent visibility/sharing and campaign-use contract (including who may use someone else's character as a contributor) plus a full-profile, event-aware native verifier covering prior DM-mixed Origins, current underlying form, source revisions and active transformations. For a strictly self-owned subset, the existing parent-owner projection could be reused as one necessary gate, but self-access alone is not authorization to claim any mixed parent or grant an unreviewed trait. Do not implement a permissive self-only production fallback without an owner-approved scope and source proof.

This is a **read-only feasibility audit** of the existing code, not a new authorization decision, a new public endpoint, or a Character Sheet modification. The two draft PRs remain independent and unmerged; the saved-profile/manifested-contributor trust boundary is still closed.
